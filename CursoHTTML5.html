🏛️ Módulo 1: Fundamentos y Contexto (El "Por Qué")

El objetivo es situar a HTML dentro de la arquitectura de sistemas que el estudiante ya conoce (o está aprendiendo).

Tema 1: El Ecosistema Web

Concepto (El Modelo Cliente-Servidor): La Web opera bajo un modelo de solicitud-respuesta (Request/Response) sobre el protocolo HTTP (Hypertext Transfer Protocol). El Cliente (usualmente un navegador web) solicita un recurso (ej. una página HTML) a un Servidor (una máquina que aloja el recurso). El servidor procesa la solicitud y envía una respuesta, que incluye el documento HTML.

Teoría (La Separación de Responsabilidades): El desarrollo web moderno se basa en un principio clave de ingeniería: la Separación de Responsabilidades (Separation of Concerns).

  • HTML (Estructura): Es la capa de datos y estructura. Define qué contenido hay (un título, un párrafo, un formulario). Es el "sustantivo".
  • CSS (Presentación): Es la capa de presentación. Define cómo se ve el contenido (colores, fuentes, layout). Es el "adjetivo".
  • JavaScript (Comportamiento): Es la capa de lógica. Define cómo interactúa el contenido (validar un formulario, mostrar un pop-up, cargar datos asincrónicamente). Es el "verbo".

Autoría (Estándares Web): El "autor" de HTML no es una sola persona.

  • Tim Berners-Lee: Se le atribuye la invención de la World Wide Web y la creación del HTML original (c. 1990) como un lenguaje para compartir documentos científicos en el CERN.
  • W3C (World Wide Web Consortium): Históricamente, fue el cuerpo de estandarización que definía las especificaciones de HTML (ej. HTML 4.01).
  • WHATWG (Web Hypertext Application Technology Working Group): Actualmente, es el grupo (compuesto por Google, Apple, Mozilla, Microsoft) que mantiene el Estándar Vivo (Living Standard) de HTML5. Para un ingeniero, esto es clave: HTML no es un estándar estático, sino uno que evoluciona continuamente.

Ejemplo Práctico (Flujo de Solicitud):

  1. Usuario escribe www.miuniversidad.edu en el navegador.
  2. Navegador (Cliente) envía una HTTP GET / request al servidor de miuniversidad.edu.
  3. Servidor localiza el archivo (ej. index.html), lo lee y lo empaqueta en una HTTP Response.
  4. Respuesta (Payload): HTTP/1.1 200 OK (código de estado) seguido de Content-Type: text/html y el código HTML.
  5. Navegador recibe el texto HTML, lo parsea y comienza a construir el DOM. Si encuentra <link rel="stylesheet" href="style.css">, hace otra solicitud HTTP para obtener ese archivo.

Tema 2: Anatomía de un Documento HTML

Concepto (El Documento Mínimo): Un documento HTML es un archivo de texto plano que sigue una estructura jerárquica específica, interpretada por el navegador.

Teoría (Modos del Navegador): La primera línea, <!DOCTYPE html>, no es una etiqueta HTML. Es una instrucción (un "preámbulo") para el navegador.

  • Su presencia activa el "Modo Estándar" (Standards Mode), donde el navegador intenta renderizar la página siguiendo las especificaciones del W3C/WHATWG al pie de la letra.
  • Su ausencia o una declaración incorrecta (ej. de HTML 4) puede activar el "Modo Quirks" (Quirks Mode), un modo de compatibilidad hacia atrás que imita errores de navegadores antiguos. Un ingeniero siempre debe evitar el Modo Quirks.

Teoría (La Estructura de Nodos):

  • <html>: El nodo raíz del documento.
  • <head>: Contiene metadatos (datos sobre el documento). No es visible para el usuario.
    • <meta charset="UTF-8">: Declara la codificación de caracteres. Es vital para la correcta visualización de tildes, 'ñ' y otros caracteres (evita "mojibake"). UTF-8 es el estándar de facto.
    • <meta name="viewport" ...>: Instrucción para navegadores móviles sobre cómo escalar la página (fundamental para el diseño responsive).
    • <title>: El título que aparece en la pestaña del navegador. Es crucial para el SEO y la accesibilidad.
    • <link>: Para vincular recursos externos (ej. CSS, favicons).
  • <body>: Contiene el contenido visible para el usuario.

Ejemplo Práctico (Plantilla de Inicio):

<!DOCTYPE html>
<html lang="es"> <!-- lang="es" es crucial para accesibilidad y SEO -->
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    
    <!-- Título para la pestaña del navegador y SEO -->
    <title>Página de Ejemplo - Ingeniería de Sistemas</title>
    
    <!-- Vinculación a la hoja de estilos CSS -->
    <link rel="stylesheet" href="css/estilos.css">
</head>
<body>
    <!-- Contenido visible aquí -->
    <h1>Mi Primera Página Web</h1>
    <p>Este es un párrafo.</p>
    
    <!-- Vinculación a JavaScript (usualmente al final) -->
    <script src="js/app.js"></script>
</body>
</html>

🏛️ Módulo 2: Semántica Estructural (El "Esqueleto")

El enfoque aquí es la diferencia crítica entre <div> y las etiquetas semánticas. Esto es vital para la accesibilidad y el SEO.

Tema 1: Texto y Contenido

Concepto (Jerarquía de Información): Los encabezados (<h1> a <h6>) no son para definir tamaños de fuente. Son para definir la estructura y jerarquía del documento.

Teoría (El "Outline" del Documento): El navegador y los motores de búsqueda usan estos encabezados para construir un "índice" o "outline" del contenido.

  • Debe haber uno y solo un <h1> por página, que representa el título principal (correlacionado con el <title>).
  • La jerarquía no debe saltarse (ej. un <h2> no debe ir seguido de un <h4> sin un <h3> intermedio).

Concepto (Importancia vs. Estilo):

  • <b> (Bold) y <i> (Italic): Son etiquetas de estilo visual. La especificación de HTML5 les ha dado un significado leve (ej. <i> para términos técnicos o en otro idioma), pero su uso principal es visual. Generalmente, esto debería hacerse con CSS.
  • <strong> (Importancia) y <em> (Énfasis): Son etiquetas semánticas.
    • <strong>: Indica que el contenido tiene una gran importancia, seriedad o urgencia. Los lectores de pantalla lo pueden anunciar con una entonación diferente.
    • <em>: Indica un énfasis en el texto, cambiando el significado de la frase.

Autoría (Especificación WHATWG): La especificación define <strong> como "contenido de gran importancia" y <b> como "texto al que se llama la atención sin implicar importancia adicional".

Ejemplo Práctico (Texto Semántico):

  • Incorrecto (Visual): <b>Atención:</b> El examen es el <i>lunes</i>.
  • Correcto (Semántico): <strong>Atención:</strong> El examen es el <em>lunes</em>. (El énfasis cambia el significado; no es el martes, es el lunes).
  • Correcto (Uso de <i>): El término <i>Hypertext</i> fue acuñado por Ted Nelson.

Tema 2: Listas y Enlaces

Concepto (Hipervínculo): La etiqueta <a> (ancla) es el pilar de la "H" en HTML (Hypertext). Convierte un documento en parte de una red.

Teoría (Atributos de <a>):

  • href: (Hypertext Reference) El atributo más importante. Define el destino del enlace.
  • target="_blank": Instruye al navegador para abrir el enlace en una nueva pestaña.
  • Implicación de Seguridad (para Ingenieros): Cuando se usa target="_blank", la nueva página tiene acceso (limitado) a la página original vía window.opener. Un atacante podría cambiar la página original (ej. a un sitio de phishing). Para prevenir esto, siempre se debe agregar rel="noopener noreferrer".
    • noopener: Evita el acceso a window.opener.
    • noreferrer: Evita que se envíe la cabecera Referer (de dónde vienes).

Ejemplo Práctico (Enlaces Seguros):

<!-- 1. Enlace externo seguro -->
<a href="https://www.google.com" target="_blank" rel="noopener noreferrer">
  Ir a Google
</a>

<!-- 2. Enlace interno (Ancla a un ID) -->
<a href="#seccion-formularios">Ir a Formularios</a>
...
<h2 id="seccion-formularios">Sección de Formularios</h2>

<!-- 3. Enlace de Email -->
<a href="mailto:profesor@universidad.edu">Contactar al Profesor</a>

<!-- 4. Enlace de Teléfono (para móviles) -->
<a href="tel:+59177712345">Llamar a Soporte</a>

Tema 3: El Diseño Semántico (HTML5 Layout)

Concepto ("Div Soup"): Antes de HTML5, las páginas se estructuraban usando contenedores genéricos <div> con IDs (ej. <div id="header">, <div id="menu">, <div id="footer">). Esto es "Div Soup" (Sopa de Divs).

Teoría (El "Por Qué" Semántico): La "Div Soup" no tiene significado para las máquinas.

  • Accesibilidad (A11y): Un lector de pantalla no puede "saltar al contenido principal" si todo son <div>s.
  • SEO: Un motor de búsqueda no puede diferenciar fácilmente el contenido principal de la publicidad en <aside>.

Teoría (Etiquetas de Layout HTML5):

  • <header>: Contenedor para la cabecera (logo, título del sitio, <nav>).
  • <nav>: Contenedor para la navegación principal (menú).
  • <main>: Define el contenido principal y único de la página. Debe haber solo uno. Es crucial para que los lectores de pantalla puedan "saltar" directamente aquí.
  • <article>: Define un contenido autocontenido e independiente (un post de blog, una noticia, un producto). Debe tener sentido por sí solo si se sindica (RSS).
  • <section>: Define una agrupación temática de contenido. Usualmente tiene un encabezado (<h2>).
  • <aside>: Define contenido tangencialmente relacionado (barra lateral, publicidad, biografías).
  • <footer>: Define el pie de página (info de contacto, copyright, enlaces secundarios).

Ejemplo Práctico (Layout Semántico):

<body>
  <header>
    <h1>Logo y Título del Sitio</h1>
    <nav>
      <ul>
        <li><a href="/">Inicio</a></li>
        <li><a href="/cursos">Cursos</a></li>
      </ul>
    </nav>
  </header>

  <main>
    <article>
      <h2>Título del Artículo Principal</h2>
      <p>Contenido del artículo...</p>
      <section>
        <h3>Comentarios</h3>
        <p>Comentario 1...</p>
      </section>
    </article>
  </main>

  <aside>
    <h3>Cursos Relacionados</h3>
    <ul>
      <li>Curso de CSS</li>
      <li>Curso de JavaScript</li>
    </ul>
  </aside>

  <footer>
    <p>&copy; 2025 Mi Universidad. Todos los derechos reservados.</p>
  </footer>
</body>

🏛️ Módulo 3: El Document Object Model (DOM)

Para ingenieros, el DOM es el concepto más importante. Es la estructura de datos que manipularán.

Tema 1: ¿Qué es el DOM?

Concepto (El DOM no es HTML):

  • HTML: Es un archivo de texto (un string).
  • DOM (Document Object Model): Es la representación en memoria de ese documento. Es una API (Interfaz de Programación de Aplicaciones) que el navegador crea después de parsear (analizar) el HTML.

Teoría (Una Estructura de Datos en Árbol): El DOM es una estructura de datos en árbol (Tree).

  • Se alinea perfectamente con la teoría de grafos y estructuras de datos que un Ingeniero de Sistemas estudia.
  • El <html> es el nodo raíz (root node).
  • <head> y <body> son nodos hijos (child nodes) de <html>.
  • <h1> y <p> son nodos hermanos (sibling nodes) dentro de <body>.
  • El texto dentro de un <p> es un nodo de texto (text node), hijo del nodo <p>.

Autoría (W3C DOM Specification): El DOM es un estándar del W3C, diseñado para ser independiente del lenguaje (aunque se usa mayormente con JavaScript). Define interfaces como Node, Element, Document.

Ejemplo Práctico (Visualización del Árbol):

HTML (Texto):

<html>
  <head>
    <title>Título</title>
  </head>
  <body>
    <h1>Encabezado</h1>
    <p>Hola</p>
  </body>
</html>

DOM (Árbol en Memoria):

[Document]
  └── [html]
      ├── [head]
      │   └── [title]
      │       └── [text "Título"]
      └── [body]
          ├── [h1]
          │   └── [text "Encabezado"]
          └── [p]
              └── [text "Hola"]

Tema 2: El DOM y su Relación con CSS y JS

Concepto (DOM como API): El DOM es el "puente" que conecta todo.

Teoría (El Proceso de Renderizado):

  1. El navegador descarga el HTML.
  2. Parseo de HTML: El navegador lee el HTML y construye el DOM Tree.
  3. Parseo de CSS: Paralelamente, si encuentra un <link rel="stylesheet">, descarga el CSS y construye el CSSOM (CSS Object Model), otra estructura de árbol.
  4. Render Tree: El navegador combina el DOM y el CSSOM para crear el Árbol de Renderizado (Render Tree). Este árbol solo contiene lo que se va a visualizar (omite cosas como <head> o elementos con display: none;).
  5. Layout (Reflow): El navegador calcula el tamaño y la posición exacta de cada elemento en el Render Tree (ej. "este <div> mide 300px y está a 20px del borde").
  6. Paint (Repaint): El navegador "dibuja" los pixeles en la pantalla.

Teoría (DOM y JS/CSS):

  • CSS usa Selectores para apuntar a nodos del DOM y aplicarles estilos (del CSSOM). (Ej. h1 apunta a todos los nodos [h1]).
  • JavaScript usa la API del DOM para leer y manipular esos nodos. (Ej. document.getElementById("mi-id") es un método de la API del DOM).

Ejemplo Práctico (El DOM en Acción):

HTML:

<h1 id="titulo">Hola</h1>

CSS (Selecciona el nodo):

#titulo {
  color: blue; /* Apunta al nodo [h1#titulo] y le aplica estilo */
}

JavaScript (Manipula el nodo):

// 1. Selecciona el nodo usando la API del DOM
const miTitulo = document.getElementById("titulo");

// 2. Manipula el nodo (cambia su contenido)
// Esto provocará un "Reflow" y "Repaint"
miTitulo.textContent = "¡Adiós!";

🏛️ Módulo 4: Formularios – La Interfaz con el Backend

Esta es la conexión directa entre el frontend y los sistemas del lado del servidor que un ingeniero construirá.

Tema 1: La Etiqueta <form>

Concepto (El Contenedor de Datos): La etiqueta <form> agrupa un conjunto de controles de entrada que envían datos a un servidor.

Teoría (Atributos Clave):

  • action: Especifica la URL del endpoint en el servidor que recibirá y procesará los datos (ej. /api/login, /registrar.php).
  • method: Especifica el Método HTTP a usar para la solicitud.

Teoría (GET vs. POST): Esta es una decisión de arquitectura de sistemas.

  • method="GET":
    • Cómo envía: Los datos del formulario se codifican en la URL (Query String).
    • Ejemplo: /buscar?q=html&lang=es
    • Propiedades: Es idempotente (múltiples solicitudes idénticas tienen el mismo efecto), es cacheable, es visible en el historial y en los logs del servidor (¡NUNCA USAR PARA DATOS SENSIBLES como contraseñas!), y tiene un límite de longitud.
    • Uso: Búsquedas, filtros, paginación.
  • method="POST":
    • Cómo envía: Los datos se envían en el cuerpo (Body) de la solicitud HTTP.
    • Propiedades: No es idempotente (enviar dos veces puede crear dos registros), no es cacheable, los datos no son visibles en la URL (más seguro para datos sensibles), y no tiene límite de tamaño.
    • Uso: Inicios de sesión, registros de usuario, crear nuevos datos.

Ejemplo Práctico (Formulario de Login):

<!-- 
Esta solicitud se enviará como un HTTP POST
a la URL "https://api.miuniversidad.edu/v1/login"
-->
<form action="https://api.miuniversidad.edu/v1/login" method="POST">
  <!-- Controles (inputs) van aquí -->
</form>

Tema 2: Controles de Formulario (Inputs)

Concepto (Key-Value Pair): El objetivo de un formulario es construir un conjunto de pares clave-valor (key-value) para enviar al servidor.

Teoría (El Atributo name):

  • El atributo id es para vincular el <label> y para JS/CSS.
  • El atributo name es la clave (key) que usará el servidor. Si un input no tiene name, su valor NO se envía al servidor.

Teoría (La Importancia de <label>):

  • El <label> es crucial por dos razones:
    1. Accesibilidad (A11y): Vincula semánticamente el texto con el control. Un lector de pantalla leerá el label cuando el usuario enfoque el input.
    2. Usabilidad (UX): El usuario puede hacer clic en el texto del label para enfocar o activar el input.
  • Se vincula usando el atributo for del label con el id del input.

Ejemplo Práctico (Campos de Registro):

<form action="/registro" method="POST">
  <!-- 
  Se enviará como: "usuario=john.doe"
  -->
  <div>
    <label for="user">Nombre de Usuario:</label>
    <input type="text" id="user" name="usuario">
  </div>
  
  <!-- 
  Se enviará como: "clave=abc123"
  type="password" enmascara la entrada
  -->
  <div>
    <label for="pass">Contraseña:</label>
    <input type="password" id="pass" name="clave">
  </div>
  
  <!-- 
  Se enviará como: "curso=sistemas"
  El 'value' del 'option' seleccionado
  -->
  <div>
    <label for="carrera">Carrera:</label>
    <select id="carrera" name="curso">
      <option value="sistemas">Ing. de Sistemas</option>
      <option value="civil">Ing. Civil</option>
    </select>
  </div>
  
  <!-- 
  Se enviará (o no) como: "terminos=on"
  -->
  <div>
    <input type="checkbox" id="terms" name="terminos">
    <label for="terms">Acepto los términos</label>
  </div>
  
  <button type="submit">Enviar Registro</button>
</form>

Tema 3: Formularios Avanzados (HTML5)

Concepto (Validación del Lado del Cliente): HTML5 introdujo atributos para que el navegador valide los datos antes de enviarlos.

Teoría (Validación: Cliente vs. Servidor):

  • Validación de Cliente (HTML5): Es una mejora de UX (Experiencia de Usuario). Ahorra tiempo al usuario y reduce solicitudes innecesarias al servidor. (Ej. required, type="email", pattern="[a-z]+", minlength="8").
  • Validación de Servidor (Backend): Es una medida de SEGURIDAD. Es obligatoria e innegociable. Un usuario malicioso puede saltarse fácilmente la validación de HTML (editando el DOM o enviando una solicitud con curl o Postman). El servidor siempre debe desconfiar del cliente y re-validar todos los datos.

Ejemplo Práctico (Validación de Cliente):

<form action="/api/v1/usuarios" method="POST">
  <!-- 
  - required: El navegador no enviará el form si está vacío.
  - type="email": El navegador validará el formato básico.
  -->
  <div>
    <label for="email_inst">Email Institucional:</label>
    <input type="email" id="email_inst" name="email" required>
  </div>
  
  <!--
  - minlength="8": Requiere al menos 8 caracteres.
  - pattern=".*[0-9].*": (Expresión Regular) Requiere al menos un número.
  - title: Muestra un tooltip con la ayuda si el patrón falla.
  -->
  <div>
    <label for="pass">Contraseña (mín 8 car, 1 num):</label>
    <input type="password" id="pass" name="password" 
           required minlength="8" 
           pattern=".*[0-9].*"
           title="Debe tener 8+ caracteres y al menos 1 número.">
  </div>
  
  <button type="submit">Crear Cuenta</button>
</form>

🏛️ Módulo 5: Multimedia y Contenido Embebido

Tema 1: Imágenes

Concepto (Imágenes y Contenido): <img> es una etiqueta "vacía" (no tiene cierre) que reserva un espacio para una imagen.

Teoría (El Atributo alt): El alt (texto alternativo) es el atributo más importante.

  • No es un tooltip (para eso es title).
  • Es el contenido equivalente si la imagen no carga (ruta rota, mala conexión).
  • Es lo que los lectores de pantalla leen a usuarios con discapacidad visual.

Teoría (Ingeniería): Si la imagen es decorativa (un borde, un fondo), el alt debe estar presente pero vacío (alt=""). Esto le dice al lector de pantalla que la ignore. Si la imagen transmite información (un gráfico, un diagrama), el alt debe describir esa información.

Teoría (Rendimiento y srcset): Enviar una imagen de 4000px a un móvil es mala ingeniería (desperdicia datos y batería).

  • El atributo srcset permite al navegador elegir la imagen más apropiada según el tamaño de la pantalla (viewport) y la densidad de píxeles (ej. pantallas Retina).
  • El navegador (el cliente) toma la decisión; el HTML solo le da las opciones.

Ejemplo Práctico (<img> Responsiva):

<!-- 1. Imagen simple con buen 'alt' -->
<img src="diagrama-cliente-servidor.png" 
     alt="Diagrama de flujo mostrando un cliente (navegador) 
          haciendo una solicitud HTTP a un servidor, 
          y el servidor enviando una respuesta HTML."
     width="500" height="300">
     
<!-- 2. Imagen responsiva con srcset (para rendimiento) -->
<img 
  srcset="logo-pequeño-1x.jpg 500w,
          logo-pequeño-2x.jpg 1000w,
          logo-grande-1x.jpg 1500w,
          logo-grande-2x.jpg 3000w"
  sizes="(max-width: 600px) 500px, 1500px"
  src="logo-grande-1x.jpg" <!-- Fallback -->
  alt="Logo de la Universidad">

Tema 2: Audio y Video

Concepto (Multimedia Nativa): Antes de HTML5, se requerían plugins (como Flash) para reproducir audio y video, lo cual era un infierno de seguridad y compatibilidad.

Teoría (APIs Nativas): <audio> y <video> son interfaces de HTML5 que le dan al navegador control nativo sobre la reproducción.

Teoría (Múltiples Fuentes): No todos los navegadores soportan los mismos codecs (ej. H.264 vs. WebM vs. AV1).

  • La etiqueta <source> (hija de <video> o <audio>) permite ofrecer múltiples formatos. El navegador usará el primero que entienda.
  • Esto es un patrón de diseño de mejora progresiva (progressive enhancement).

Ejemplo Práctico (Video con Fallback):

<video controls width="640" height="360" poster="preview.jpg">
  <!-- 
  'poster' es la imagen de vista previa.
  'controls' muestra los controles nativos.
  -->
  
  <!-- El navegador intentará cargar WebM (preferido por ser abierto) -->
  <source src="conferencia.webm" type="video/webm">
  
  <!-- Si falla, intentará cargar MP4 (H.264, alta compatibilidad) -->
  <source src="conferencia.mp4" type="video/mp4">
  
  <!-- Texto para navegadores muy antiguos o si todo falla -->
  Lo sentimos, tu navegador no soporta video nativo.
  <a href="conferencia.mp4">Descarga el video aquí</a>.
</video>

Tema 3: Embebidos Externos

Concepto (<iframe>): Un "inline frame" o <iframe> incrusta un contexto de navegación completamente separado (una página web entera) dentro de la página actual.

Teoría (Costos y Riesgos):

  • Rendimiento: Cargar un <iframe> es costoso. Es como lanzar un navegador dentro de tu navegador. Bloquea el onload de la página principal.
  • Seguridad: Si no se configuran bien, son un vector de ataque para Clickjacking (mostrar un sitio malicioso invisible sobre tu sitio para robar clics).

Teoría (Atributos de Seguridad y Rendimiento):

  • sandbox: Restringe fuertemente lo que el <iframe> puede hacer (ej. sandbox="allow-scripts" solo permite scripts, pero no pop-ups ni acceso al DOM padre).
  • loading="lazy": (Moderno) Instruye al navegador para que no cargue el <iframe> (ej. un video de YouTube al final de la página) hasta que el usuario haga scroll cerca de él. Mejora drástica del rendimiento.

Ejemplo Práctico (Embed de YouTube optimizado):

<!-- 
Este es el código que YouTube proporciona, 
optimizado para rendimiento y seguridad 
-->
<iframe 
  width="560" 
  height="315" 
  src="https://www.youtube.com/embed/VIDEO_ID_AQUI" 
  title="Descripción del video para accesibilidad"
  frameborder="0" 
  allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture" 
  allowfullscreen
  loading="lazy"> <!-- Carga diferida -->
</iframe>

🏛️ Módulo 6: Tablas – Solo para Datos Tabulares

Tema 1: La Mala Práctica Histórica

Concepto (Tablas para Layout): En los 90s y principios de 2000, antes de que CSS (especialmente Flexbox y Grid) madurara, los desarrolladores usaban <table> para definir la estructura de la página (ej. una tabla de 3 columnas para col-izquierda, contenido, col-derecha).

Teoría (Por qué es Pésimo):

  • Semántica Incorrecta: Mezcla datos (HTML) con presentación (CSS), rompiendo la "Separación de Responsabilidades".
  • Accesibilidad Nula: Un lector de pantalla intentará leer una página web diseñada con tablas de forma lineal (fila por fila, celda por celda), haciendo el contenido incomprensible.
  • Rendimiento: Los navegadores deben cargar la tabla entera antes de poder calcular su layout y renderizarla.
  • Mantenimiento: Es una pesadilla de colspan y rowspan anidados.

Tema 2: Estructura de Tablas Semánticas

Concepto (Datos Tabulares): El uso correcto de <table> es para mostrar datos que tienen una relación bidimensional (filas y columnas), como una hoja de cálculo.

Teoría (Estructura Semántica):

  • <table>: El contenedor principal.
  • <caption>: Un título para la tabla, crucial para accesibilidad.
  • <thead>: Agrupa el contenido de la cabecera de la tabla.
  • <tbody>: Agrupa el cuerpo principal de datos.
  • <tfoot>: Agrupa el pie de la tabla (ej. totales, sumas).
  • <tr>: (Table Row) Define una fila.
  • <th>: (Table Header) Define una celda de encabezado. Es la "clave" de la columna o fila.
  • <td>: (Table Data) Define una celda de datos.

Teoría (Accesibilidad con scope): El atributo scope le dice explícitamente al lector de pantalla qué datos encabeza el <th>.

  • scope="col": Este <th> es el encabezado de toda la columna.
  • scope="row": Este <th> es el encabezado de toda la fila.

Ejemplo Práctico (Horario de Clases):

<table border="1"> <!-- border=1 solo para depuración, usar CSS -->
  <caption>Horario de Clases - Semestre 1</caption>
  
  <thead>
    <tr>
      <th scope="col">Hora</th>
      <th scope="col">Lunes</th>
      <th scope="col">Martes</th>
      <th scope="col">Miércoles</th>
    </tr>
  </thead>
  
  <tbody>
    <tr>
      <th scope="row">08:00 - 09:30</th> <!-- Encabezado de fila -->
      <td>Cálculo I</td>
      <td>Álgebra Lineal</td>
      <td>Cálculo I</td>
    </tr>
    <tr>
      <th scope="row">09:30 - 11:00</th>
      <td>Programación I</td>
      <td>Física I</td>
      <td>Programación I</td>
    </tr>
  </tbody>
  
  <tfoot>
    <tr>
      <td colspan="4">Periodo de exámenes: 15-19 de Julio</td>
      <!-- 'colspan' indica que esta celda ocupa 4 columnas -->
    </tr>
  </tfoot>
</table>

🏛️ Módulo 7: HTML Avanzado y Buenas Prácticas

Tema 1: Accesibilidad Web (A11y)

Concepto (A11y): Acrónimo de "Accessibility" (11 letras entre A e Y). Es la práctica de asegurar que tus aplicaciones web sean usables por todas las personas, incluyendo aquellas con discapacidades (visuales, auditivas, motoras, cognitivas). No es una "mejora", es un requisito (a menudo legal).

Autoría (WCAG): Las Web Content Accessibility Guidelines (WCAG) del W3C son el estándar de oro. Definen niveles de conformidad (A, AA, AAA).

Teoría (WAI-ARIA): HTML semántico (usar <nav>, <button>, <main>) cubre el 80% de la accesibilidad básica. Pero, ¿qué pasa si creas un componente complejo (ej. un menú desplegable) usando <div>s y JavaScript? Un <div> no tiene semántica.

  • ARIA (Accessible Rich Internet Applications) es un conjunto de atributos HTML que añaden semántica para los lectores de pantalla.
  • role: Define el "rol" del elemento (ej. role="button" en un <div> le dice al lector "esto es un botón").
  • aria-*: Define estados y propiedades (ej. aria-expanded="true" en un menú, aria-label="Cerrar" en un botón X).

Teoría (La Primera Regla de ARIA): "No uses ARIA". Es decir, siempre prefiere usar un elemento nativo de HTML antes que "parchar" un <div> con ARIA.

  • Mal: <div role="button" onclick="...">Click</div> (No funciona con teclado, no tiene estados focus/hover).
  • Bien: <button onclick="...">Click</button> (Ya es accesible por defecto).

Ejemplo Práctico (ARIA para un Checkbox Personalizado):

<!-- 
Un 'checkbox' personalizado donde el <input> real está oculto
y se usa un <span> con estilo.
-->
<span 
  role="checkbox" <!-- Le dice al lector de pantalla que es un checkbox -->
  aria-checked="true" <!-- El estado actual (manejado por JS) -->
  tabindex="0" <!-- Permite que sea enfocable con el teclado -->
>
  Activar notificaciones
</span>

Tema 2: HTML y SEO (Search Engine Optimization)

Concepto (SEO): El proceso de optimizar un sitio web para que los motores de búsqueda (crawlers, bots) como Google puedan entenderlo, indexarlo y posicionarlo alto en los resultados.

Teoría (El Crawler es un "Usuario" Ciego): El bot de Google es, en esencia, un usuario ciego y sin CSS. HTML Semántico es SEO Técnico.

  • Google usa tu <h1> para entender el tema principal.
  • Usa los <h2> para las subsecciones.
  • Usa el alt de las <img> para entender las imágenes.
  • Entiende que el contenido en <main> es más importante que en <aside>.

Teoría (Metadatos para Crawlers):

  • <meta name="description">: La descripción que aparece bajo tu título en Google. No afecta el ranking, pero sí la tasa de clics (CTR).
  • <meta name="robots">: Instrucciones para el crawler (ej. nofollow, noindex).

Teoría (Protocolo Open Graph): Creado por Facebook, es un conjunto de metadatos meta que controlan cómo se ve tu página cuando se comparte en redes sociales.

Ejemplo Práctico (Un <head> Optimizado):

<head>
  <title>Curso de HTML para Ingenieros | Mi Universidad</title>
  
  <!-- SEO Básico -->
  <meta name="description" content="Aprende HTML5 desde la semántica 
       hasta la integración, enfocado en estudiantes de ingeniería.">
  
  <!-- Open Graph (para Facebook, LinkedIn, etc.) -->
  <meta property="og:title" content="Curso de HTML para Ingenieros">
  <meta property="og:description" content="Enfocado en estructura y backend.">
  <meta property="og:image" content="https://miuniversidad.edu/img/curso-html.jpg">
  <meta property="og:url" content="https://miuniversidad.edu/cursos/html">
  <meta property="og:type" content="website">
  
  <!-- Twitter Card (similar a OG) -->
  <meta name="twitter:card" content="summary_large_image">
</head>

Tema 3: Validación y Calidad de Código

Concepto (HTML Válido): Escribir HTML que se adhiere estrictamente a las especificaciones del WHATWG.

Teoría (Por qué Validar): El HTML es un lenguaje permisivo. Si olvidas cerrar una etiqueta, el navegador intentará adivinar lo que quisiste decir (a esto se le llama "error handling").

  • El Problema: Diferentes navegadores (Chrome, Firefox, Safari) pueden adivinar de formas diferentes.
  • Esto lleva a que el DOM Tree sea impredecible. Un DOM impredecible es imposible de manipular con JS de forma fiable.
  • Ingeniería: Un ingeniero busca sistemas predecibles. Validar tu HTML (ej. con el Validador del W3C) asegura que tu estructura base (el DOM) será la misma en todos los navegadores estándar.

Ejemplo Práctico (Error Común y Validación):

HTML Inválido:

<!-- ERROR: Un elemento 'inline' (<a>) no puede
     contener un elemento 'block' (<h1>) -->
<a href="#">
  <h1>Ir al Inicio</h1>
</a>

<!-- ERROR: <p> no puede contener otro <p> -->
<p>Primer párrafo. <p>Segundo párrafo.</p></p>

Resultado del Parseo (Impredecible): El navegador "corregirá" el segundo error así:

<p>Primer párrafo. </p>
<p>Segundo párrafo.</p>
<p></p> <!-- Un párrafo vacío fantasma -->

HTML Válido (Correcto):

<h1>
  <a href="#">Ir al Inicio</a>
</h1>

<p>Primer párrafo.</p>
<p>Segundo párrafo.</p>

🏛️ Módulo 8: Proyecto Final y Siguientes Pasos

Tema 1: El Puente a CSS y JavaScript

Concepto (Los "Ganchos" - Hooks): HTML proporciona los "ganchos" (hooks) para que CSS y JS se "agarren".

Teoría (ID vs. Class): Esta es la analogía de base de datos para un ingeniero.

  • id (Identificador):
    • Debe ser único en todo el documento.
    • Es una Clave Primaria (Primary Key).
    • Usos:
      • CSS: #mi-id (selector de alta especificidad, usar con moderación).
      • JS: document.getElementById('mi-id') (la forma más rápida de seleccionar un elemento).
      • HTML: Anclas (<a href="#mi-id">) y <label for="mi-id">.
  • class (Clase):
    • Es reusable. Un elemento puede tener múltiples clases (class="btn btn-primary") y múltiples elementos pueden tener la misma clase.
    • Es una Relación Muchos-a-Muchos (Many-to-Many).
    • Usos:
      • CSS: .mi-clase (el método preferido para estilizar).
      • JS: document.querySelectorAll('.mi-clase') (para seleccionar grupos de elementos).

Ejemplo Práctico (Combinación):

<!-- 
'id' es único (para el formulario en sí)
'class' es reusable (para la apariencia)
-->
<form id="form-registro" class="formulario-modal" action="..." method="POST">
  
  <!-- 'class' usada para estilizar todos los inputs iguales -->
  <label for="user-reg">Usuario:</label>
  <input id="user-reg" name="user" type="text" class="input-text">
  
  <!-- 'class' también usada para variantes (BEM) -->
  <button class="btn btn--primary">Registrar</button>
  <button class="btn btn--secondary">Cancelar</button>
</form>

Tema 2: El Mundo Real (Generación de HTML)

Concepto (HTML Estático vs. Dinámico): Un ingeniero de sistemas rara vez escribirá 50 archivos .html estáticos. El HTML se genera dinámicamente.

Teoría (Arquitectura 1: Renderizado en Servidor - SSR):

  • Cómo funciona: El cliente solicita /perfil. El servidor (ej. un backend en Java/Spring, Python/Django, PHP/Laravel, Node/Express) recibe la solicitud.
  • Consulta la base de datos para obtener los datos del usuario.
  • Usa un Motor de Plantillas (Template Engine) (ej. Thymeleaf, Jinja2, Blade, EJS).
  • Este motor fusiona una plantilla HTML con los datos.
  • Ejemplo de Plantilla (Blade/Laravel): 
    <h1>Perfil de {{ $usuario->nombre }}</h1>
<p>Email: {{ $usuario->email }}</p>
  • El servidor envía el HTML ya renderizado (HTML puro) al cliente.
  • Ventajas: Rápido primer render (FCP), buen SEO.

Teoría (Arquitectura 2: Renderizado en Cliente - CSR / SPAs):

  • Cómo funciona: El cliente solicita la app. El servidor envía un index.html casi vacío y un archivo JavaScript enorme (ej. React, Vue, Angular).
  • El navegador ejecuta el JS.
  • El JS (React) realiza una solicitud a una API (ej. GET /api/perfil) que devuelve JSON, no HTML.
  • React usa ese JSON para construir el DOM dinámicamente en el navegador del cliente.
  • Ejemplo (JSX de React): (Parece HTML, pero es JS) 
    function Perfil({ usuario }) {
  return (
    <div>
      <h1>Perfil de {usuario.nombre}</h1>
      <p>Email: {usuario.email}</p>
    </div>
  );
}
  • Ventajas: Experiencia de "app" fluida, sin recargas de página.

Conclusión para el Ingeniero: No importa si usas SSR o CSR, el resultado final que el navegador debe entender es HTML Válido y Semántico. Los frameworks son solo herramientas para generar ese HTML de manera eficiente.

Proyecto Final

Consigna: Crear un Portafolio de Ingeniero de Sistemas o la Landing Page de un Proyecto de Software (real o imaginario).

Requisitos (Checklist de Ingeniería):

  1. Validación W3C: Debe pasar sin errores.
  2. Semántica de Layout: Debe usar <header>, <main>, <footer> y al menos un <section> y un <article> (para un proyecto).
  3. Formulario: Debe incluir un formulario de contacto (<form>) con method="POST", action (puede ser un placeholder) y validación de cliente (required, type="email").
  4. Accesibilidad (A11y):
    • Cada input debe tener un <label> vinculado.
    • Todas las <img> deben tener alt (o alt="" si son decorativas).
    • Jerarquía de encabezados (<h1>, <h2>) lógica.
  5. SEO (Metadatos): Debe tener un <title> único y un <meta name="description">.
  6. Multimedia: Debe incluir al menos una imagen optimizada y un <iframe> (ej. un mapa de ubicación o un video demo).
  7. Siguientes Pasos (Opcional): Vincular un archivo style.css (Módulo CSS) y un app.js (Módulo JS) aunque estén vacíos, preparando la estructura.
